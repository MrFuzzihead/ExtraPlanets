# ExtraPlanets Codebase Analysis — Findings

> Generated by code review of the `main` branch. Date: 2026-08-17.
> Scope: `src/main/java` (active 1.7.10 build) — the `migrate/` tree (1.12.2 port + vendored
> Galacticraft) is not part of the active build and is excluded.

## Fix status

- ✅ **P0 — Rover damage threshold bug** — resolved in `EntityVehicleBase.java` & `EntityPoweredVehicleBase.java` (threshold `> 2` → `> 40`, matching vanilla `EntityBoat`).
- ✅ **P0 — Space suit oxygen from any single piece** — resolved in `Tier1SpaceSuitArmor.java` (`handleGearType` restricted per piece; `canBreathe` now requires the full four-piece suit).
- Remaining P1/P2 items are not yet addressed.
- ⏸️ **Space suit vs. GC oxygen gear — deferred by design decision (2026-08-17).** Keeping the current fix (full suit replaces the GC mask + gear harness; `canBreathe` requires the full 4-piece suit; GC oxygen tanks are still required and drained via `GCPlayerHandler.checkOxygen`'s `!airEmpty` gate). The concern — the suit is currently cheap and has no power / radiation / pressure cost, so letting it replace GC gear is generous — is acknowledged but shelved until the suit mechanics (electric/power, pressure, radiation, tanks) are fleshed out later.

## What this is

**ExtraPlanets** is a **Minecraft 1.7.10 Forge mod** and a **Galacticraft addon** that adds 10+
planets, 12+ moons, 4 extra solar systems (Kepler systems), rocket tiers 4–10, rovers, bosses,
custom machines, armor, fluids, and worldgen.

- **~1,230 Java source files** in `src/main/java` (~9.7 MB).
- Package layout: `planets/` (387), `moons/` (321), `client/` (111), `blocks/` (80), `items/` (83),
  `entities/` (42), `inventory/` (40), `tileEntities/` (34), `world/` (22), `armor/` (18), plus
  `api/`, `nei/`, `network/`, `recipes/`, `handlers/`, `proxy/`, `util/`.
- Build: migrated to the **GTNH RetroFuturaGradle** convention (`build.gradle.kts` →
  `com.gtnewhorizons.gtnhconvention`), Forge `10.13.4.1614`, targeting `1.7.10`. Depends on
  Galacticraft 3.4.33-GTNH, NotEnoughItems, ForgeMultipart, CodeChickenCore, optional Mekanism/CoFH.

**Recent work (active branch):** a Tier-1 Space Suit (in-progress, ~8 commits), and ore-dictionary
additions.

## Critical bugs / findings

### P0 — Rovers are destroyed by a single small hit (damage threshold bug)

In **both** rover classes:
- `EntityVehicleBase.java:217`
- `EntityPoweredVehicleBase.java:213`

```java
if (flag || this.dataWatcher.getWatchableObjectInt(this.currentDamage) > 2) {
    ... setDead(); dropBuggyAsItem();
}
```

This is derived from vanilla `EntityBoat`, which uses **`> 40`**. Here the threshold is `2` — 20× too
low. Since each hit adds `damage * 10` to `currentDamage`, **any hit above 0.2 damage (i.e. any punch
or fall) instantly destroys the rover and drops it as an item.** Mars/Venus rovers are effectively
unusable as vehicles. Likely a copy-paste regression from vanilla.

### P0 — Space suit provides oxygen/breathe from *any single piece*

`Tier1SpaceSuitArmor.java`:

```java
public boolean canBreathe(ItemStack helmetInSlot, EntityPlayer playerWearing, IBreathableArmor.EnumGearType type) {
    return true;                    // regardless of gear type
}
public boolean handleGearType(IBreathableArmor.EnumGearType gearType) {
    return true;                    // all gear types qualified
}
```

`canBreathe` ignores `type`, so the **helmet *and* even boots/leggings** all report the suit as
breathable. In GC's model, oxygen delivery is keyed to the head piece + oxygen tanks. As written,
*any* single suit piece grants full breathing (no tanks required). Combined with `EnumGearType`
handled for everything, this is likely exploitable / bypasses the intended "full suit" requirement.
If a self-contained suit is intended, it should check that the chest tank is present / sufficient
oxygen, not blanket-return `true`.

### P1 — Fragile shared static render state (Space Suit renderer)

- `ArmorCustomModel.poseSource` is a **static** field set in `RenderPlayerEvent.Pre` and cleared in
  `Post` (`SpaceSuitRenderHandler.java:65,112`).
- `Tier1SpaceSuitArmor.models` is a **static `HashMap<Integer, ArmorSpaceSuitModel>` shared by all
  players** (`:33,136`).
- `SpaceSuitRenderHandler` stores prev-gear flags in **instance fields** (`:55–59`).

This works only because rendering is single-threaded and Pre/Post are strictly paired. It breaks if:
- a `Pre` fires without a matching `Post` (e.g. a render exception), leaking a stale
  `poseSource`/gear flags into subsequent renders;
- any non-player entity renders while `poseSource` is non-null (armor stands, other mods'
  third-person renders) — the suit then copies *that* pose.

Also `ArmorCustomModel.renderFlatPart/renderFlatOnly/renderFlatGlass` mutate global GL state
(`glDisable(GL_TEXTURE_2D)`, `glBlendFunc`, `glColor4f`) and only restore some of it — if a part
throws, blend/texture state leaks and corrupts subsequent rendering.

### P1 — Biome IDs use positive defaults in 1.7.10's fixed 256-slot list

`Config.java` defaults such as:
```
"Venus Biome ID", 145   "Mercury Biome ID", 148   "Jupiter Biome ID", 150 ...
```
And the biomes are created as `public static final ... = new BiomeGenVenus(Config.venusBiomeID)` —
i.e. **initialized on class load even when the planet is disabled in config**. In 1.7.10
`BiomeGenBase.biomeList` is a fixed array; positive IDs here risk colliding with other mods' biomes
(many use 128+). If a user disables Venus but the class loads anyway, the biome still claims slot 145.
Forge supports negative biome IDs for mod biomes (which is what Galacticraft itself uses); using fixed
positive IDs is a real-world corruption risk.


### P1 — `new Random()` allocated every tick + per-tick weather effects

`MainHandler.java:33-50`: `onPlayer` (a `PlayerTickEvent`) does `new Random()` **every tick** and has
a ~1% chance to `addWeatherEffect(new EntityLightningBolt(...))` **near every player entity** ticking
in the Jupiter dimension on that client. This is wasteful (RNG + weather-effect allocation per player
per tick) and only exists client-side.

Related: **`Config.jupiterLightingServer` is loaded but never used anywhere** (dead config — the
server-side lighting feature was never implemented; only `jupiterLightingClient` is consulted).

### P1 — `getArmorTexture` can return `null`

`Tier1SpaceSuitArmor.java:60` returns `null` for the fallback case. In 1.7.10 `RenderBiped` binds
`getArmorTexture(...)`; a `null` return can NPE / hit the missing-texture path. In practice only the
four suit pieces reach this method, so low risk — but it's a latent crash.

### P1 — `OreDictionary.getOres("ingotCopper").get(0)` without an empty-check

`ExtraPlanets_Recipes.java` furnace recipes (e.g. `:64-65`) call `.get(0)` on ore-dict lists. If
"ingotCopper"/"ingotTin" aren't registered by another mod, this throws `IndexOutOfBoundsException` at
postInit and crashes the game. GC normally registers these, so it works in practice, but it's fragile
against config options that disable GC ore registration.

### P1 — Network packet lacks bounds-checks on packet type

`PacketSimple.decodeInto` does `EnumSimplePacket.values()[buffer.readInt()]` (`:92`) without
validating the ordinal. A malformed/offset packet throws `ArrayIndexOutOfBoundsException`; it's
swallowed by a `try/catch`, but a hostile client can push garbage onto the channel.

### P1 — Client/server config are never synchronized

`Config.init()` reads the **local** `config/ExtraPlanets.cfg` on both sides (`ExtraPlanets.java:185`).
Dimension IDs, biome IDs, schematic GUI/page IDs, and feature toggles must match between client and
server but there's no sync/validation. If they differ, players get "dimension mismatch" disconnects or
chunk desync. (Standard for the era, but the combinatorial config here makes it likely.)

### P1 — `MainHandler` registered on both Forge & FML buses

`ExtraPlanets.java:188` registers it on `MinecraftForge.EVENT_BUS` (both sides), and
`ClientProxy.java:175` also registers it on `FMLCommonHandler.instance().bus()` (client). The
client-only `FogDensity` / `GuiOpenEvent` / `CelestialBodyRenderEvent` methods are
`@SideOnly(Side.CLIENT)`; the `onPlayer`/`onThermalArmorEvent` are fine. It works, but the split
registration is easy to break (a method without `@SideOnly` referencing a client class would crash
dedicated servers).

## Code-quality / maintainability observations

- **Massive copy-paste in worldgen.** Files like
  `planets/*/worldgen/village/StructureComponent*VillageHouse.java` (each ~59 KB) and
  `StructureComponent*VillageWoodHut.java` are near-identical except for class/package name — there
  are ~15+ copies. `WorldGenVolcano.java` is 111 KB. This is the single biggest maintenance and
  bug-propagation risk (a fix must be re-applied to every copy).
- **Swallowed exceptions everywhere.** Hundreds of `catch (Exception e) {}` / `catch (Throwable e) {}`
  (village `MapGen*` static-init blocks, `CustomCelestialSelection` render path,
  `ExtraPlanets_MicroBlocks:365`). Failures are invisible.
- **`System.out.println` / `printStackTrace()`** scattered through the active source
  (`CustomCelestialSelection:669`, `PacketSimple`, etc.) instead of a logger.
- **`@SuppressWarnings` + raw types** in `ItemMarsRover.onItemRightClick` and many containers — but
  these match GC's own patterns.
- **Dead/vestigial options:** `jupiterLightingServer` (unused), plus overlapping legacy compat flags
  (`morePlanetsCompatibility`, `morePlanetsCompatibilityAdv143`, `morePlanetsCompatibilityNew`, etc.)
  which are easy to misconfigure and disable the wrong things.
- The **`migrate/` tree** (1.12.2 port + vendored `micdoodle8/mods/galacticraft` and `mjrlegendslib`)
  massively inflates the repo and pollutes IDE searches/builds. Not referenced by `build.gradle.kts`,
  but it makes the working tree confusing.

## Optimizations worth doing

1. **Cache one `Random`** in `MainHandler` (or better, gate on the existing per-tick chance + throttle)
   instead of `new Random()` per tick.
2. **Refactor the duplicated village/volcano worldgen** into shared, parameterized templates (big win
   — eliminates ~1 MB+ of copy-paste and the "fix must be applied N times" problem).
3. **Replace swallowed exceptions / `System.out`** with a proper logger (`GCLog`/`FMLLog`), at least
   under a `Config.debugMode` guard.
4. **Guard `OreDictionary.getOres(...)`** with `isEmpty()` fallbacks to avoid hard crashes when
   optional mods are absent.
5. **Validate packet type ordinal** before indexing `EnumSimplePacket.values()`.
6. **Fix the rover hit threshold** (the `> 2` → `> 40`-style regression) so rovers survive hits
   sensibly.
7. **Reconsider positive biome IDs** — move to negative IDs (GC convention) or at least document /
   reserve against the `BiomeGenBase` 256-slot limit, and don't register biomes for planets that are
   disabled.
8. **Remove dead config keys** (`jupiterLightingServer`) or implement the feature they promise.

1. **P0 – Rover durability bug** (gameplay-breaking and clearly a regression).
2. **P0 – Space suit `canBreathe`/`handleGearType` logic** (intended suit mechanics; decide & enforce
   "full suit" vs. piece-carrying-oxygen).
3. **P1 – Biome ID strategy** (collision/corruption risk) + don't load disabled-planet biomes.
4. **P1 – Recipe ore-dict `.get(0)` guards.**
5. **P1 – Packet ordinal validation + MainHandler RNG caching.**
6. **P2 – Render-state robustness** (`poseSource`, static model sharing, GL state restore).
7. **P2 – Worldgen copy-paste refactor** (longest-term maintainability win) and log hygiene.
